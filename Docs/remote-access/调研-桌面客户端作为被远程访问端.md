# 调研：DeepSeek Harness 桌面客户端（Electron）作为「被远程访问的一端」

> 日期：2026-10-29
> 环境：Windows 10，DSH 桌面版 **0.2.1-rc.3**（asar 内 desktop 包 `@deepseek-ai/dsh-desktop`）
> 安装目录：`C:\Users\Administrator\AppData\Local\Programs\DeepSeek Harness\resources\app.asar`（内含 `dsh/`）
> 运行实例：`127.0.0.1:65145`（Owner 进程 `DeepSeek Harness.exe`，PID 86340）
> profile：`C:\Users\Administrator\.dsh\profiles\desktop\`
>
> 本文是**带日期的只读快照**：全程未改动任何文件、未重启/未杀 DSH、未改 profile 配置。
> 唯一例外是本仓库 `Docs/remote-access/` 下新增的这篇文档。

> 结论分三档标注：**【实测】**（跑了命令看输出）、**【代码证据】**（asar 内文件 + 代码片段）、**【推测】**（由代码合理外推，未验证）。

## 一句话结论

**桌面客户端这条链路在技术上「能被打通」，但缺的是「启动 token」这一环，而 token 在设计上不可外部获取。**

- 桌面 App 的 web 服务由**子进程**（`dsh-desktop-host`，Electron Node 模式）启动，参数固定为 `--no-open --host 127.0.0.1 --port 0`；端口由 OS 分配，端口号从 `ctx.webServer.port` 读，**带 token 的 URL 只经 Node IPC 回给 Electron 主进程**，不进日志、不进文件、不进 `DSH_WEB_URL`。
- 桌面窗口加载的是自定义协议 `dsh-app://app/`，主进程把请求转发给 Host，并在内存里持有 `hostCookie`。**token 与 cookie 都只存在于内存**。
- **不用 token ⇒ 必然 401**（`/`、`/api`、`/connect` 全部）。cookie 签名绑定 `host:port`（authority），换端口即失效。
- 因此「公司机只跑桌面客户端 + 家里 `ssh -L 3099:127.0.0.1:65145`」：**默认无解**（第一个请求 401，且永远拿不到 token）。
- 但存在两条**绕过 token 的可行路径**（都不需要改 DSH 本体）：
  1. **凭据层**：cookie 只用 `$DSH_HOME/.credentials.yaml` 里明文保存的 HMAC 密钥签名 ⇒ 可在公司机上为**任意 authority（含转发端口 3099）离线铸造 cookie**。**【实测已跑通】**：为 `127.0.0.1:3099` 铸造 cookie 并用 `Host: 127.0.0.1:3099` 访问 → **200 + 完整首页**（这就是 ssh -L 的等价模拟）。
  2. **插件层（官方 API）**：同进程插件可调 `ctx.connection.authenticatedUrl(...)` 拿到带 token 的 URL —— 已装的社区插件 **`dsh-mobile` 正是这么做的**，而且它此刻已经在 `10.11.152.117:8080` 上跑着带 TLS 与设备配对的网关。
- **改 profile 配置解决不了 token 问题**：`webserver`/`connection`/`web-runtime` 三个行都能配（host/port/trustedHosts/publicUrl/cookieMaxAgeDays），但**没有任何字段能预设或导出 token**。

```js
async function authenticateWebHost(url) {
  const response = await fetch(url, { redirect: "manual" });
  const cookie = response.headers.get("set-cookie");
  await response.body?.cancel();
  if (response.status !== 303 || cookie === null) throw new Error("Desktop Host authentication failed");
  const end = cookie.indexOf(";");
  return end < 0 ? cookie : cookie.slice(0, end);      // 只留 "name=value"
}
```

页面本体不是从 HTTP 加载的：窗口加载 `dsh-app://app/`（`main.js:12135`），主进程把每个请求转发给 Host 并**注入内存 cookie**，并把 `set-cookie` **从响应里剔除**（`main.js:8244-8256`、`8269-8299`）：


首登（`authorizeIndex`，`:458-497`）：

### trustedHosts 的语义（`:240-250`，`:777-780`）

```js
function isTrustedApiRequest(request, trustedHosts, bindHost, protocol = "http:") {
  const host = header$1(request.headers, "host");
  if (host === void 0) return false;
  const hostUrl = parseAuthority(host, protocol);
  if (hostUrl === void 0) return false;
  if (!isLoopbackHostname(hostUrl.hostname) && !isTrustedAuthority(hostUrl, trustedHosts, protocol)
      && !isBindAddressAuthority(hostUrl, bindHost)) return false;
  if (header$1(request.headers, "sec-fetch-site") === "cross-site") return false;
  const origin = header$1(request.headers, "origin");
  if (origin === void 0) return true;
  return isSameAuthorityOrigin(origin, host);

```

- `127.0.0.1` / `localhost` / `[::1]` **天然可信，端口不限** ⇒ ssh -L 到 loopback 端口**不需要** `trustedHosts`。
- 端口省略的 `trustedHosts` 条目匹配任意端口；写端口的只匹配该端口。
- `Origin` 缺失（curl、直连导航）直接放行；`sec-fetch-site: cross-site` 一律拒。

## 四、profile 配置能力：行 id、config schema、示例 patch

### 4.1 承载 web 服务的行（`dsh/node_modules/@deepseek-ai/dsh-web-app/cordis.patch.yml`）

```yaml
    - id: web-startup                     # name: '@deepseek-ai/dsh-web-app/startup'
      name: '@deepseek-ai/dsh-web-app/startup'

    - id: webserver                       # 监听器
      name: '@deepseek-ai/dsh-host-webserver'
      inject: [webStartup]
      config:
        host: !!js ctx.webStartup.host ?? '127.0.0.1'
        port: !!js ctx.webStartup.port ?? 3080
        tls: !!js ctx.webStartup.tls
        compression: gzip
        compressionLevel: 1
        compressionThresholdBytes: 1024

    - id: web-runtime                     # 打印 URL / 打开浏览器 / publicUrl
      name: '@deepseek-ai/dsh-web-app'
      inject: [webStartup]
      config:
        openBrowser: !!js ctx.webStartup.openBrowser

        publicUrl: !!js ctx.webStartup.publicUrl

    - id: connection                      # 鉴权 + 信任栅栏
```

同文件开头两行是关键约束（原文）：

> 3: `# Applied after dsh-base's insert; rows here override base rows by id, with`
> 4: `# the profile's own cordis.patch.yml and any --patch overlays still to come.`
> 6: `# A patch replaces the targeted row's whole config, so each row below`
> 7: `# restates every key it owns.`

⇒ **profile（`~/.dsh/profiles/desktop/cordis.patch.yml`）可以用 `- id: webserver` / `connection` / `web-runtime` 覆盖它们；但 config 是「整块替换」，必须把要保留的键全部重写。**

## 五、`ssh -L` 场景的可行性判定

前提：公司机只跑桌面客户端（loopback:65145），家里 `ssh -L 3099:127.0.0.1:65145`。

### 5.1 不额外做什么 ⇒ 不可行

1. 家里浏览器打开 `http://127.0.0.1:3099/` ⇒ Host = `127.0.0.1:3099`（loopback ⇒ 栅栏放行），但没有 cookie ⇒ **401**（实测同一路径 401）。
2. 想靠 `?token=` 首登 ⇒ 需要进程 token，而 token：
   - 只在 Host 子进程内存里，
   - 只经 Node IPC 给 Electron 主进程，
   - 由 Host 打印的 `dsh web: <带 token 的 URL>` 行（`web-runtime.printUrl: true`）被 `pipe(process.stdout)` 接到 Electron 的 stdout —— 正式 Windows GUI 包里没有可读的 stdout【推测：GUI 子系统进程无控制台句柄，写入被丢弃】，
   - **绝不写文件**（实测 userData 全目录 grep 0 命中），
   - **绝不进 `DSH_WEB_URL`**（`README.zh.md:84` 明说「凭据也绝不会出现在模型上下文或 `DSH_WEB_URL` 中」）。
3. 想先在公司机用带 token 的 URL 换 cookie、再把 cookie 搬到家里 ⇒ 也不行：
   - cookie **绑定 authority**，签到 `:3099` 时名字和 payload 都不匹配 ⇒ **401**（已实测）。
   - 除非本地转发端口也用 **65145**（authority 相同），但即便如此，也没人能拿到那个 cookie（它在 Electron 主进程内存里，且 `set-cookie` 被扣掉，浏览器 cookie jar 里没有）。

**缺的那一环：启动 token（或等价的主人身份凭据）。** 这一步在桌面客户端里是「只进不出」的。

### 5.2 补救路径一（凭据层，实测已跑通，非官方特性）

cookie 只用 `.credentials.yaml` 里明文密钥的 HMAC 签名，所以**可以在公司机上离线铸造任意 authority 的 cookie**：

```bash
# 公司机（或透过 ssh 在公司机执行），给转发端口 3099 铸一张 cookie
node -e '
const c=require("node:crypto"),f=require("node:fs");
const s=Buffer.from(/secret:\s*([A-Za-z0-9_-]+)/u.exec(f.readFileSync(process.env.HOME+"/.dsh/.credentials.yaml","utf8"))[1],"base64url");
const auth="127.0.0.1:3099", b=x=>Buffer.from(x).toString("base64url"), now=Date.now();
const body=b(JSON.stringify({version:1,authority:auth,issuedAt:now,expiresAt:now+30*864e5}));
console.log("dsh-auth-"+b(c.createHash("sha256").update(auth).digest())+"=v1."+body+"."+b(c.createHmac("sha256",s).update(body).digest()));'
```

把这串 `name=value` 在**家里浏览器**里写给 `127.0.0.1`（DevTools → Application → Cookies，或 `document.cookie` 不行因为 `HttpOnly` ⇒ 只能靠手工添加/注入），之后 `http://127.0.0.1:3099/` 直接 200。

- 【实测等价性】我用同样方法为 `127.0.0.1:3099` 铸 cookie，用 `Host: 127.0.0.1:3099` 打本机 65145 → **200 + 完整首页**（43 947 字节）。这就是 ssh -L 的效果。
- 优点：不用改 DSH、不用重装插件、不用重启桌面 App；cookie 在重启后仍有效（密钥稳定）。
- 缺点/风险：**这是凭据层操作，不是官方支持的功能**；等价于「拿到主人身份」。需要公司机的文件读权限（有 ssh 就有）。有效期默认 30 天（可用 `connection.cookieMaxAgeDays` 调），泄露即长期有效。

### 5.3 补救路径二（插件层，官方 API —— 本机已经装了一个）

**进程内插件**可以合法拿到带 token 的 URL：`connection` 服务暴露 `authenticatedUrl(baseUrl)`（`connection/lib/index.js:811-813`）。已装的社区插件 `dsh-mobile` 就是这么干的（`~/.dsh/profiles/desktop/node_modules/dsh-mobile/lib/index.mjs:18440`）：

```js
function upstreamAuthenticatedUrl(ctx, upstreamOrigin) {
  const connection = ctx.connection;
  if (typeof connection?.authenticatedUrl !== "function") return void 0;
  const authenticatedUrl = connection.authenticatedUrl(upstreamOrigin.origin);
  ...
```

然后 `exchangeUpstreamCookie()`（`:7250` 起）拿这个 URL 发一次 `GET`，从 `303 + set-cookie` 里截出 `name=value` 自己保存、给所有转发请求注入。

**而且它此刻就在跑**：

```
TCP  10.11.152.117:8080  0.0.0.0:0  LISTENING  86340 (= DeepSeek Harness.exe)
```

`.dsh/mobile-access/setup.json`：`listenPort: 8080`、`upstreamOrigin: http://127.0.0.1:65145`、`tls.mode: managed`（自带 CA/证书）、`extraAllowedCidrs: [10.11.0.0/16, 10.10.0.0/24, 10.10.18.0/24]`；`.dsh/mobile-access/devices.json` 里有 4 台已配对的 Android 设备（只存 token 摘要）。它自己还有 frp / cloudflared / cpolar 相关的错误码（`frp_component_launch_failed`、`cloudflared_*`、`cpolar_*`），意味着也支持隧道出网。

⇒ **「公司机只跑桌面客户端、家里要访问」这个需求，本机已经有一个在跑的现成答案（dsh-mobile 网关 + 设备配对 + TLS），不需要再写插件，也不需要 ssh -L。**

另外 `dsh-mobile` 源码注释里提到另一个社区插件 **`dsh-lan-access` 的 `noAuth: true`**：它把 `authenticatedUrl` 换成一个返回裸 origin 的函数 ⇒ 等于**关掉 DSH 的浏览器鉴权**。这是一条「配置层面彻底免除 token」的路子（代价是端口上任何人可进），供决策参考。

### 5.4 有没有 Electron 特有的「仅本机」限制？

**没有。** 逐项核对：

| 可能的形式 | 结论 |
|---|---|
| 检测 UA / 要求 Electron UA | 无（服务端不看 UA；纯 curl 带 cookie 得 200） |
| 要求 `X-Requested-With` / 自定义头 | 无 |
| `Origin: file://` 之类 | 无；`origin` 缺失直接放行（`isTrustedApiRequest:247-249`） |
| 检测 DSH 自己的自定义头 | 无（`x-dsh-auth-token` 只出现在**账号平台视图**的禁用头名单里，`main.js:3679`） |
| `dsh-app://` 协议限制 | 那是 Electron 内部转发器（`forwardWebRequest`）对**自己渲染进程**的要求（`origin` 必须是 `dsh-app://app`），与外部 HTTP 访问无关 |
| 只接受 `sec-fetch-site: same-origin` | 否：只有 `cross-site` 被拒，`same-site`/`none`/缺失都放行（已实测） |

唯一「Electron 专属」的差别是：桌面窗口走自定义协议 + 主进程代发请求，所以**浏览器里那套 cookie 机制根本没被用到**——这也是为什么从磁盘上找不到 cookie。

### 7.1 A. `dsh --profile desktop web` 可行吗？—— **不可行（设计上禁止）**

【实测】

【代码证据】`dsh/node_modules/@deepseek-ai/dsh/lib/bin.js:36-38` 与 `:113`：

```js
...
```

`manageDesktopProfile: true`（桌面自带的 `dsh-desktop-host/lib/cli.js` 传的）**只放开 `dsh plugin --profile desktop ...`**（`:120`），**不放开 boot**。第三方插件 `dsh-ops` 的注释也印证：

⇒ 「用同一个 desktop profile 从 CLI 起服务拿 token」这条路**被官方封死**。

**可行的替代（需用户决策，本轮未执行）**：把 `~/.dsh/profiles/desktop` **整目录复制**成另一个名字（例如 `desktop-cli`），再 `dsh desktop-cli --no-open --port 3080`。此时：
- 插件一个不少（`package.json` 的 `dsh.profile.bundles`、`node_modules`、`link:` 依赖都跟着复制）；
- 能打印带 token 的 URL；
- 副作用：profile 名不再是 `desktop`，于是 `ui-sidebar-browser`、`desktop-product-telemetry`、`product-analytics` 三行按 `!!js` 条件变成禁用（`dsh-web-app/cordis.patch.yml:46-60、297-299`）。

**② 插件是否有「只能在 Electron 里跑」的依赖？** —— **没有检出**。

对 `~/.dsh/profiles/desktop/node_modules` 里这 13 个第三方包做了 `require('electron') | from 'electron' | process.versions.electron | electronAPI` 全量扫描：**0 命中**（`dsh-better-sidebar`、`dsh-chat-import`、`dsh-context`、`dsh-ctx-menu`、`dsh-ide-git`、`dsh-mcp-compat`、`dsh-mnemon`、`dsh-mobile`、`dsh-ops`、`dsh-plugin-upgrader`、`dsh-svn-tools`、`dsh-win-notify`、`hooks-adapter`）。

第一方包里只有 4 处提 `process.versions.electron`，且都不影响纯 CLI 启动：

- `dsh-skill-office`：**有** Electron 时要求显式 `config.node`（桌面宿主注入了 `{runtimeDir,source,root}`，纯 CLI 分支反而更简单）；
- `dsh-tool-fs-search`：asar 路径 → `.asar.unpacked` 的改写（纯 CLI 下不走）；
- 客户端 PDF 预览 / 第三方 `open`、`sharp`：与宿主无关。

⇒ **纯 CLI 起这份插件清单，功能上不会因 Electron 缺失而报错**（唯一可预期差别是 7.1 里那三行 desktop-only 行被禁用）。

**③ 桌面 App 正在跑时再用 CLI 起同一 profile 会冲突吗？**
- **同一 profile 名**：目前无法启动（7.1 已被拒），所以不存在这种冲突。
- **复制出来的新 profile 名**：没有进程级单实例锁（全 asar 搜 `already running` / `singleInstance` / instance lock，第一方包 0 命中；Electron 的 `lockfile` 只在 userData 里，属于另一个 profile 体系）。真正的共享点是 `$DSH_HOME` 下的：
  - `sessions/`、`storages/`（会话/存储，SQLite）；
  - `.credentials.yaml`（只读键值，两边都用同一个签名密钥 —— 这反而是好事，铸出的 cookie 两边通用）；

### 7.2 B. 能不能从运行中的 Electron 实例拿到 token？—— **没有官方途径**

| 途径 | 结论 |
|---|---|
| IPC / preload | 无。`ready.url`（含 token）只在主进程与 Host 子进程之间；preload 暴露的是 `dsh-app://` 应用的 UI IPC（`assertProductSender` 校验 sender/frame），不含 token |
| `dsh` 子命令 | 无。桌面自带的 `dsh.cmd` 只做 profile/plugin 管理，且 boot desktop 被拒（7.1） |
| `/api/*` 端点回显 | 无。所有 `/api` 都过 `admit()`，需要先有 cookie；没有任何"给我 token/给我 URL"的端点 |
| 写文件 | 无。`printUrl` 只 `console.log`；`crash-host.log` 只捕获 **stderr** 尾巴（`main.js:3815-3817`），URL 行走 stdout |
| 日志级别 / 调试开关 | 无运行时开关。`--inspect=127.0.0.1:PORT` **只在开发态**（`developmentHostInspectPort(development)`） |
| 环境变量 | `DSH_WEB_URL` 明确**不含凭据**（`web-app/lib/index.js:150-155` + `README.zh.md:84`） |
| 读 Electron cookies 库 | **不可靠且通常为空**：`set-cookie` 被 `forwardWebRequest` 主动剔除（`main.js:8244-8256`），换 cookie 用的是 Node `fetch`（不进 Chromium 存储）。实测该 sqlite 文件被运行中进程独占锁（`Device or resource busy`），无法读取 |

**能拿到 token 的两种「非外部」方式**：① 写一个挂在同一 Host 的 Host-侧插件，调 `ctx.connection.authenticatedUrl(...)`（官方 API，`dsh-mobile` 就是这么干的）；② 用 CLI 起同一套 profile（见 7.1 的复制方案），从终端读那行 `dsh web:`。

**「读 cookies 库拷 cookie」要说清**：即使能读到，cookie 也**和端口强绑定**（`authority = host:port` 同时进 cookie 名与签名 payload，`connection/lib/index.js:307-316/335-337/566`）。本地转发端口必须与远端同号（例：都是 65145）才可能命中，换端口一律 401（已实测）。且这是**非官方、不可靠**的路径。

### 7.3 C. CSP / X-Frame-Options：会不会挡住 iframe 嵌入？—— **响应头完全不设，不挡；但 API 栅栏会挡跨站**

【实测】带合法 cookie 的首页响应头（原始）：

```
HTTP/1.1 200 OK
content-type: text/html; charset=utf-8
Vary: Accept-Encoding
Date: Thu, 29 Oct 2026 02:42:26 GMT
Transfer-Encoding: chunked
```

—— **没有 `Content-Security-Policy`，没有 `X-Frame-Options`，没有 `X-XSS-*` / `Referrer-Policy`**。首页 `<head>` 里也只有 `<meta charset>` 和 `<meta viewport>`，**没有 meta CSP**。

【代码证据】全 asar 扫 `frame-ancestors` / `X-Frame-Options` / `Content-Security-Policy`：

- `frame-ancestors` 唯一的第一方命中在 `dsh-deepseek-account-platform/lib/index.js:1137`（账号平台自己的内嵌页面：`default-src 'none'; script-src 'nonce-...'; frame-ancestors 'none'`）—— **与 DSH 主 UI 无关**；
- 其余命中全在 `dsh-experimental-inspector` 的 DevTools 静态件（Lighthouse/Chromium 模型）与第三方 `undici`；
- `dsh-host-webserver` / `dsh-web-app` / `dsh-client-connection` 三个包对这三个词：**0 命中**。

⇒ **`dsh-remote-dsh` 那类「用 iframe 把 A 的页面嵌进 B」的方案不会被响应头拦住。** 但真正会拦的是鉴权栅栏（`isTrustedApiRequest`）：

| 嵌入场景 | 结果 |
|---|---|
| 同一台机器、同一 host 不同端口（如 B 在 `127.0.0.1:3099`，iframe 指 `127.0.0.1:65145`） | iframe 文档自身的 origin 就是被嵌方，API 请求的 `Origin` = `http://127.0.0.1:65145` = Host ⇒ 过栅栏；`sec-fetch-site` 为 `same-site`（IP 视作独立 site，端口不影响）⇒ 也过。**技术上可嵌，但需要 cookie 存在**（cookie 是 host-only、`SameSite=Strict`；same-site 下会发送）【推测：浏览器对 IP 字面量的 same-site 判定按 host，端口无关；未做真实浏览器验证】 |
| 跨站嵌入（例如在外网域名页里嵌公司机 DSH） | `sec-fetch-site: cross-site` ⇒ **403**；`Origin` 不匹配 ⇒ **403**。页面壳能显示，但所有 API 全 403，等于不可用 |
| 若把 iframe 指到 ssh 隧道端口（`127.0.0.1:3099`） | 页面能载入（Host 是 loopback），但 **401**（缺该 authority 的 cookie），与顶层导航一样 |

## 八、给决策的三句话

1. **桌面客户端本身不能当「远程可访问的一端」用**：token 只进不出、cookie 只活在主进程内存、换端口即失效。这不是配置问题，是设计。
2. **要绕过去只有三条路**：① 换一个非保留 profile 用 CLI 起（拿得到 token，插件可整套复制）；② 走凭据层（用 `.credentials.yaml` 的密钥离线铸 cookie，实测可行，但属主人级凭据操作）；③ **直接用社区插件**（本机 `dsh-mobile` 已经在 8080 上跑着 TLS + 设备配对 + 隧道组件的完整实现）。
3. **`trustedHosts` / `publicUrl` 只能解决「403」，解决不了「401」**——它们是信任栅栏，不是身份。想要 token-free 访问，只有 `dsh-lan-access` 的 `noAuth: true` 那种「关掉鉴权」的做法（代价自负）。
