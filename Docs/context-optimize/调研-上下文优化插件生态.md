## 0. 一句话结论

「上下文优化」在 DSH 生态里已经**不是一个插件，而是一整条产品线**——按机制至少分六类，
每类都有 5～30 个实现。真正稀缺的不是「压缩」，而是**「删掉的东西还能拿回来」+「不打断前缀缓存」**
这两件事同时做到；目前只有少数几个插件（CREMATOR、compaction-instant、infinite-context、argp）
在这条线上认真做。

### 2.1 CREMATOR 的「随时焚化」到底是什么（已读 README）

发布形态：npm `cremator-dsh@0.1.3`（另有 `cremator-opencode`、`@cremator/core`），
一条 `dsh plugin --profile web add cremator-dsh` 装完，Plugins 页出现 CREMATOR，
斜杠菜单出现 `/cremate`。

核心机制（六条，按重要性排）：

1. **只删工具结果**——任何规则、判决、问询都不能把用户消息或模型自身输出列为候选。
2. **确定性证明直接删，不问模型**——「过期读」「被重读取代」这两类由代码证明已死，直接移除；
   判断有用性这件事，确定性代码永远不做。
3. **剩下的交给模型，一行一个结果**——表格问询（table ask）里每行给路径、总行数、几处行锚点，
   模型只回答 keep / forget。表格永不重复结果正文。
4. **应用是 rewind + append，不是 edit**——回退到被遗忘的单元，保留所有没点名的节点，
   再追加回执。**共享前缀一个字节都不改，所以还能命中缓存。**
5. **每次删除都可逆**——被删字节进 append-only trash ledger（`<DSH_HOME>/storages/cremator/sessions/N/ledger.sqlite`），
   带 recall id；`necromancy` 工具按 id 逐字节还原，重启后仍然有效。
6. **两档触发**：token 水位（`pruneThresholdTokens`，需配 `contextWindowTokens`）自动跑，
   `/cremate` 手动随时跑。

配置项（`dsh --patch` 的 `config`）：`barBytes`(512) / `enforcement`(apply|record-only) /
`contextWindowTokens` / `pruneThresholdTokens` / `entryAskTrigger` / `nativeCompactionBackstop` 等。

> 定位判断：CREMATOR 是**「压缩后端 + 可逆账本」**这一类里设计最讲究的一个，
> 但它自己 README 明确写了 **「本库不建立任何对回答质量的影响」**——它优化的是 token 与窗口，
> 不是正确率。这一点在选型时很重要。

## 5. 空位在哪：自研 vs 用现成

### 5.1 已经被做透的（不要重复造）

- 上下文**观测 / 环形图 / 面板** —— `dsh-context` 5570 星 + 官方实名推荐，没有胜算。
- **阈值配置** —— 十几个薄壳，纯配置项，没有护城河。
- **摘要式压缩后端** —— 十几个实现，同质化严重。
- **跨会话记忆** —— MemOS / mneme / mnemonic 一大片。

### 5.2 仍然稀缺的组合（真正的空位）

1. **「可逆删除」× 「缓存前缀零损伤」×「零模型调用」三者同时成立**。
   目前 compaction-instant 有 1+3、CREMATOR 有 1+2、argp 有 1+3 但都要模型参与事务。
   **没有一个做到「确定性 + 可逆 + 缓存友好 + 零调用」四件套。**
2. **删除决策的「可解释性」**：CREMATOR 有回执（receipt），但回执是给模型看的；
   没有一个插件给**人**看「这一轮为什么删了这条、删了多少 token、省了多少钱」的可审计账本。
3. **跨插件的上下文预算仲裁**：现在每个插件各自削各自的，没有「全局预算分配器」
   （谁该让路、让多少）。B 类里 `dsh-context-toolkit` 两头堵是最接近的，但不做仲裁。
4. **压缩后的「正确率回归」度量**：CREMATOR 自己承认「不建立任何对回答质量的影响」。
   生态里缺一个「压缩前 vs 压缩后同题重放」的评测插件——`dsh-infinite-context` 的
   `bench-results/` 是仓库内自测，不是通用工具。

### 5.3 三条路，按投入排

| 路线 | 做什么 | 投入 | 风险 |
|---|---|---|---|
| **A. 直接用现成** | 装 `dsh-context`（观测）+ `compaction-instant`（零成本压缩） | 10 分钟 | 无；但拿不到差异化 |
| **B. 自研「确定性 + 可逆 + 缓存友好 + 零调用」四件套** | 填 5.2 的 1 号空位 | 中（1～2 周） | 要啃 DSH 的 compaction 缝与 session log 格式 |
| **C. 自研「上下文预算仲裁器」** | 填 5.2 的 3 号空位：全局预算、谁让路、让多少，带人可读账本 | 中高 | 要理解所有 B 类插件的产出形态，接口面大 |

> 本仓库（`dsh-yzlin499-easy-plugins`）现有 7 个插件里没有上下文类的，
> 如果要做，B 路线与现有插件的「小而专」风格最一致；C 路线更像一个平台型产品。
