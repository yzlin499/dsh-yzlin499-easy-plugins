# 设计讨论：分层折叠 + 巡航 + 询问

> 快照日期：**2026-11-28** ｜ 本机 DSH `0.2.2-rc.5`（Desktop，asar）
> 本文是**设计讨论稿**，不是结论。事实部分标注了出处；推断部分标「推断」。

## 0. 需求复述（我的理解）

1. 不在乎前缀缓存（公司额度），只在乎**上下文健康**：让模型每一轮看到的上下文都处在「可折叠的状态」。
2. 多个任务串在一个主会话里聊十几个；对后来的模型，旧任务只该剩下「他做过这些事」。
3. **多层级折叠**：折叠本身可以再被折叠，形成层级树；总量可能几百 M。
4. 主 agent 有一个**展开工具**：调用后尽力把指定那段还原进当前窗口——因为窗口可能撑满，所以只能是「尝试」。
5. **巡航**子 agent：标注哪段可折叠、哪段不可折叠；在合适时机把主 agent 展开的收回。
6. **询问**子 agent：主 agent 通过工具向它打听「那段折叠的对话大概是什么、具体有什么」，从而不用展开。它**没有任何工具**（除了和主 agent 交互），以免多余工具污染判断。

## 1. 先给结论

### 1.1 三方插件覆盖到哪

**覆盖到的（可复用，不必重造）**

| 能力 | 现成实现 | 差距 |
|---|---|---|
| 上下文占用/构成的可信读数 | 官方 `dsh-token-meter`（`contextPressure` / `contextBreakdown` 投影）+ `bowenliang123/dsh-context`(5570★) | 无，直接用 |
| 把 surface 段折叠成一条摘要 | 官方 `compaction` seam（`compactRegion`） | 无，这是地基 |
| 折叠后原文归档 + 分页读回 | `chocobo77/dsh-infinite-context`（`memory_expand`）、`TsFreddie/dsh-compaction-instant`（`recall` / `search` / `/recall`） | 都是**单层**折叠；无层级树 |
| 按节点 `full / key / off` 三档控制模型所见 | `catsenior507/dsh-context-assembler`（上下文树 + 组装区 + 展开） | **最接近你设想的**：已有树、已有展开（单节点逐字、多节点合成一条重放消息）、已处理 tool-call 原子性。但它是**人**在面板上点，没有巡航、没有询问子 agent、没有多级折叠语义 |
| 子 agent 悄悄评估每轮并落库 | `Aik358/dsh-auto-memory`（一个子 agent 每轮评估、按主题归档） | 它是「把记忆写出去」，不是「给主会话标折叠边界」 |
| 交接/换窗 | `dsh-context-relay`、`dsh-context-rollover`、`dsh-session-handoff` | 换窗思路，与你「不换窗、就地折叠」不同 |

**没覆盖到的（这就是你的空位）**

1. **巡航**：没有任何插件把「哪段可折/不可折」做成持续标注的**独立判定者**。现有插件的折叠时机都是阈值/水位/规则/自学习系数，判定者是**代码**；你要的是**一个有判断力的观察者**，并且它的判断要落成可审计的标注。
2. **多级折叠的树形语义**：现有折叠都是「一层压成一条摘要」，折叠后的摘要不再被折叠。你要的是 `叶子 → 卡片 → 父卡片`，且**父卡片的信息必须由子卡片确定性合成**（否则每上一层就再被 LLM 改写一次，漂移会累积）。
3. **展开的「尽力而为 + 置换」**：现有展开工具（`memory_expand` / `recall`）是**读回**到工具结果里，不是**就地还原到历史位置**；也没有「窗口不够时先收别的再展」的置换逻辑。
4. **询问**：没有任何插件提供「向一个只读折叠区的子 agent 打听」这条路径。最接近的是各家的 `search_context`（工具检索），但那是主 agent 自己检索，会往主上下文里灌片段——正好是你要避免的。

### 1.2 我的判断

**值得自己做，但不要一次做完。** 原因：

- 你要的**折叠 + 展开 + 归档**三件事的地基官方已经给全了（`surfaceOp: replace` + 会话日志 append-only），三方也验证过可行；真正没人做的是**判定层**（巡航）与**问答层**（询问）。
- 这两层恰好是**最容易做错、也最容易被误判为「有用」**的部分——所以先做能验证的（折叠账本 + 展开），再上判定层。

## 2. DSH 的硬约束（这些决定设计长什么样）

以下是我在本机 asar 里读到的、会直接限制设计的六条。**这些不是建议，是物理约束。**

### 2.1 surface 只有一种变异：`replace`，没有「取消折叠」

`SurfaceOp` 只有两种：

- `{ op: 'append' }` — 常规尾部追加
- `{ op: 'replace', startSeq, endSeq }` — 遮蔽当前 surface 上这两个事件之间的**闭区间**，并在**原位置**插入新事件；`startSeq === endSeq` 只替换一个节点。

（出处：`docs/subsystems/session.zh.md` §`SurfaceOp`）

**推论（关键）**：不存在「把 replace 撤掉」的操作。所以：

- **折叠** = 追加一条 `user/message`，`surfaceOp: replace(spanStart, spanEnd)`，正文是卡片文本。
- **展开** = 追加一条 `user/message`，`surfaceOp: replace(卡片节点, 卡片节点)`，正文是原文。
- **再收起** = 再做一次单节点 replace，正文换回卡片。

这条比你想象的更好用：**展开是「就地还原」而不是「追加到尾巴」**——因为它替换的是卡片所在的那个位置，模型看到的因果顺序不变。代价是从那个位置往后的前缀全部作废（你不在乎）。

### 2.2 折叠有两条硬边界

- **不能覆盖 surface 第 0 号节点**（`system/message` / system prompt）。强行覆盖会被 surface 折叠拒绝。
- **必须保持 tool-call ↔ tool-result 配对**。官方导出 `toolPairingBalancedBefore/After` 用来验证切点；跨切点有未回答的 tool call 就是非法。现成实现（`dsh-context-assembler`）的做法是：**把折叠区扩展到整组 tool-call**，唯一例外是「只折叠单个 tool result」——此时发一条 `tool/result` 替换，`toolCallId` 不动，配对依然完整。

**推论**：折叠的**最小不可分单位不是「一条消息」，而是「一个工具调用组」**。任何按 token 数硬切的方案都会在第一个 tool pair 处翻车。

### 2.3 只能有一个压缩后端，所以它必须是「那个」后端

`ctx.compaction` 每个上下文只加载一个实现。你要接管折叠，就必须**替换 `compaction-basic`**，而不是在旁边加一个插件各自折叠——否则两个生产者会拿着不同的 surface 快照互相踩。

`CompactionEngine` 给你三个入口：

- `compactIfNeeded(agent, trigger, signal)` — 自动（`pressure` / `context-overflow`）
- `compactNow(agent, signal)` — 空闲时手动缩一次（`/compact` 走这条）
- `compactRegion(agent, start, end, signal)` — **按 surface 位置折任意显式区间**（这是你要的「折哪段」的入口）

还有一把锁：任何折叠必须先追加 `compaction/start`（log-only）再干活，最后 `compaction/end`。崩溃留下未配对的 start，下次会被识别为 busy。

### 2.4 折叠必须在「开放轮次」里执行

据 CREMATOR 的 README（引用其 ISSUE-535）：surface 替换只有在**开放的 turn** 内才被宿主接受，从命令 handler 直接跑会写坏会话存储。它的做法是：`/cremate` 先注册一个标记消息、用 `agent.followup` 开一个 turn，让 `agent/pre-step` 在 turn 内执行折叠，再把标记步骤拒掉。

**这条我未在本机独立验证**，但如果成立，它直接决定了「巡航什么时候动手」：巡航不能是任意定时器，它必须**挂在 turn 边界**上（`agent/pre-step` / turn-end）。

### 2.5 `agent/pre-step` 改不了历史，只能改「这一步进什么」

`PreStepDecision` 的两个分支是 `{ kind: 'reject' }` 与 `{ kind: 'enter', messages, startsRequestSeries? }`，后者替换的是**即将进入这一步的消息批次**（来自 inbox），不是派生历史。

**推论**：想做「每轮动态投影、完全不改日志」的路线（有些人会想），在 DSH 上**不可行**。历史只能通过 surface 变异来改。这也反过来证明你的方向是对的：折叠必须是**持久状态**，不能是每轮现算的投影。

### 2.6 子 agent 读不到被折叠的内容

- `spawn` 子 agent：「它看不到这段对话」（工具描述由 `inheritsParentContext` 决定措辞）。
- `fork` 子 agent：能继承**已完成轮次的派生内容**——但被折叠的段在 surface 上已经被遮蔽了，**fork 出来的子 agent 同样看不到**。

**推论（这条会改变你的「询问」设计）**：询问子 agent **不可能自己读到折叠内容**。它只有两种活法：

- **(a) 宿主喂**：主 agent 调 `ask_folded(spanId, question)`，宿主从归档里捞出原文，塞进子 agent 的 prompt，子 agent 只负责读+答。
- **(b) 给一支极窄的读工具**：子 agent 持有一个 `span_read(spanId, offset, limit)`，自己分页读。

你说「它没有任何工具」——(a) 完全符合，但代价是**宿主必须猜「该喂哪一段」**；猜错就要重来一轮。(b) 违背你的洁癖，但它只有一个 2 参数工具，schema 很小，且能让子 agent 自己按需翻页。**我的建议是 (a) 为主 + 结构化「要更多」的回路**（见 §4.4），而不是 (b)。

## 3. 你的设计里我认为要先钉死的三件事

### 3.1 折叠单元：不是 span，是「任务段（episode）」

按任意 token 区间折叠，折出来的卡片对后来者是**噪音**——因为模型看到的是「一段对话被压成三行」，而不是「一个已经结束的任务」。

建议：**折叠单元 = episode**，定义是

> 从一条 `user/message`（人类发起）开始，到「该任务的下一次任务切换」或「连续 N 个 turn 无工具调用」为止。

episode 才是你要的「他知道他做过这些事」的粒度。episode 内部再按需细分（工具组、失败-重试对）。

### 3.2 卡片的格式必须固定，且**父卡片由子卡片确定性合成**

这是多级折叠能不能用的分水岭。如果父卡片是「把子卡片再喂给 LLM 总结一次」，那么三层之后信息漂移会指数累积（`dsh-infinite-context` 实测：无核对的降级摘要关键锚点缺失 71.2%，带机械核对 1.1%）。

建议卡片是**固定字段的 JSON + 一行渲染**：

```jsonc
{
  "id": "ep_7f3a",              // 稳定 id，展开/询问都用它
  "span": [1240, 1388],          // surface 位置闭区间
  "turns": [41, 57],
  "tokens": 48213,
  "time": ["2026-11-28T14:02", "2026-11-28T15:31"],
  "claim": "把 MCP 配置读取从 .mcp.json 迁到 codex toml",   // 一句话，可由 LLM 写
  "facts": {                     // 确定性抽取，绝不丢
    "files": ["dsh-mcp-compat/index.js", "..."],
    "cmds": ["npm test", "..."],
    "errors": ["ERR_MODULE_NOT_FOUND: ..."],
    "decisions": ["不改 cordis.patch.yml 的挂载行"],
    "open": ["还没跑通 windows 路径"]
  },
  "children": ["ep_7f3a/1", "ep_7f3a/2"],   // 子卡片 id（多级）
  "archive": "sha256:...",       // 原文归档句柄
  "recall": 3                    // 被展开过几次（振荡保护用）
}
```

父卡片 = `claim` 重写（可 LLM）+ `facts` 取**子卡片 facts 的并集/前 N 条**（纯代码）+ `children` 列表。**facts 永不重新生成，只做合并与截断**。这条能保证「三层之后还知道自己改过哪些文件」。

### 3.3 「不可折叠」必须是一等状态，不是布尔

「这段不能折」有至少四种原因，处理方式完全不同：

| 标记 | 含义 | 何时解除 |
|---|---|---|
| `pinned` | 人钉的，永不动 | 人取消 |
| `hot` | 刚被展开过/刚被询问过，正被使用 | N 轮后自动 |
| `live` | 含未回答的 tool call / 待批准 / 待回答问题 | 配对闭合 |
| `open` | 判决里还有未闭合的 todo / 未验证的假设 | 任务段结束 |

巡航输出的是**这四种标记的组合**，不是「可折/不可折」。这点很重要：如果只有布尔，巡航必然会把「刚展开又被收回」的东西反复折，产生振荡。

## 4. 我建议加进来的设计（你没提但会咬人的）

### 4.1 展开要「置换」，不能只「尽力」

你说的「尝试展开」我认为不够：模型会反复试、反复失败，浪费轮次。建议展开工具的语义是**事务式**：

```text
expand(spanId, {budget?}) →
  { ok: true,  injected: 4210, evicted: ["ep_5c"] }        // 顺手收了别的
  { ok: partial, injected: 1200, of: 48213, next: 1200 }   // 只展了头一段
  { ok: false, reason: "no-headroom", alternatives: [...] } // 附 3 条可问的摘要
```

- **有 headroom** → 直接就地还原。
- **headroom 不够** → 先按巡航给的优先级**收回若干低优先段**，腾出空间再展（这就是「置换」）。
- **怎么都不够** → 不要返回裸错误，返回「这段的一页摘要 + 3 个可直接 `ask_folded` 的问题模板」。让模型下一步能走通。

host 端算 headroom 要用官方的 `contextPressure` 投影，别自己估。

### 4.2 展开是有「保质期」的

展开即污染：它会一直占着窗口直到被收走。所以每次展开要在账本里记一条 `expansion {span, at_turn, tokens, ttl}`，巡航在 `at_turn + ttl`（或水位回落）后收回，并在卡片上给 `recall++`。

`recall` 上去了就说明这段**真的在被反复用**——那它不该被折，或者不该折得那么深。这是你自己设计的反馈回路：**展开次数是「可折叠性」的实测标签**，比任何 LLM 判定都可信。

### 4.3 层级树不要给模型看全貌

几百 M 的树，模型看一遍就爆了。模型应该只看到：

- **最近 2–3 个 episode 原文**（不可折区）
- **上一层的卡片清单**（一行一个：id + claim + tokens）
- 再往上的层级**只显示「还有 N 个更早任务，共 X tokens」**，要看就 `context_map(parentId)` 翻一层。

也就是说：树对模型是**可导航的分页结构**，不是一次性展开的目录。这条如果不做，多级折叠会立刻变成新的上下文炸弹。

### 4.4 询问的「回路」比询问本身重要

一次问答不够——子 agent 拿到宿主喂的那一段，很可能发现「不够」。所以建议询问协议是**结构化的两轮**：

```text
主 → 询问: { spanId, question, hint? }
询问 → 主: {
  answer: "...",
  confidence: "high|low",
  evidence: [ {quote, offset} ],        // 必须带原文引用，防编
  need: null | "更多关于 <关键词>"      // 结构化「要更多」
}
```

宿主看到 `need` 就按关键词从归档里再捞一段，把 `(上次的问题, 上次的回答, 新捞的段)` 一起再给子 agent——**同一个子 agent、同一条会话**（`sendMessage` 支持驻留子级继续对话，这是官方能力）。

这样你既保住了「子 agent 没有任何工具」，又不需要宿主一次猜准。

另外：**询问子 agent 必须用独立 `agentPreset` + `toolFilter` 清空工具**。官方子 agent 有 `agentPreset` / `allowedAgentPresets` 配置项，`spawn` 后端支持独立 preset——工具集在 preset 里配，不在工具参数里配。这是唯一能把「零工具」真正落实的地方（光靠提示词说「不要用工具」是不可靠的）。

### 4.5 巡航不能读全文，否则比省的还贵

巡航最贵的错误设计是：每次把最近 50 轮全文喂给它判断。正确做法是**分层输入**：

- **确定性预筛（0 token）**：按 §3.1 切出 episode 边界、按 §2.2 校验 tool pair、按「读过的文件是否被再次读」「命令是否已经成功过」这类**可证死**的规则先标记一批。
- **结构摘要（小 token）**：给巡航的是「turn 列表 + 工具名 + 参数首行 + 结果字节数 + 首尾各一行」，不是正文。
- **LLM 判定只处理中间地带**：真正模糊的（比如「这段结论还被后面的推理引用」）才让巡航读。

再加一条硬预算：**巡航每轮 ≤ 主上下文的 2% token**。超了就不判，留给下一轮。

### 4.6 「可折叠性」的判定要可审计、可回放

巡航每次输出一份 `annotation` 记录（log-only 事件，进会话日志、不进 surface）：`{episodeId, verdict, reasons[], at, model, cost}`。

好处：出问题时能回答「为什么这段被折了」；也能离线回放「如果当时不折，模型会怎么答」——这正是整个生态缺的**压缩前后正确率回归**（`CREMATOR` 自己都写明「不建立任何对回答质量的影响」）。

### 4.7 折叠的「原子提交」与失败回滚

一次折叠 = `compaction/start` → 归档原文 → 追加卡片 replace → `compaction/end`。任何一步失败都要保证：**surface 要么是折前的样子，要么是折后的样子，不能半折**。

特别注意：归档必须先落盘、校验 sha256，**再**动 surface。顺序反了就会出现「折了但捞不回来」。

### 4.8 多 agent 协作时的折叠

你有多个子 agent（巡航/询问）时，主会话折叠会不会影响它们？——`fork` 子 agent 继承的是**派生历史**，如果你在 fork 之后折叠了父会话，子 agent 手里的历史是旧的。这通常无害（它已经带着快照在跑），但**不要指望子 agent 能看到折叠后的新视图**。设计上：子 agent 一律按「启动时的快照」处理，不要让它回读父会话状态。

## 5. 我建议的落地顺序（三阶段，各自可单独交付）

| 阶段 | 交付物 | 能验证什么 | 估算 |
|---|---|---|---|
| **P1 地基** | CompactionEngine（替换 basic）+ episode 切分 + 卡片格式 + 归档 + 就地 `expand` 工具 + 置换逻辑 + 账本 | 「折叠→展开→再收起」全链路正确，tool pair 不破，原文可逐字还原 | 主要工作量在这里 |
| **P2 判定** | 巡航子 agent（确定性预筛 + 结构摘要 + LLM 判中间）+ 四种标记 + pin/hot 维护 + 面板 | 折叠时机是否比阈值式更好；`recall` 反馈是否收敛 | 中 |
| **P3 问答** | 询问子 agent（独立 preset 零工具）+ 结构化 `need` 回路 + 归档检索 | 「不展开也能问到」的命中率；子 agent 成本是否低于展开成本 | 小 |

**P1 单独就有价值**：即使永远不上巡航，一个「能就地展开、能逐字还原、能按 episode 折」的后端，也比现在所有单层摘要式压缩强。**P2 是风险最高的部分**（判定质量决定体验），所以放第二。**P3 最便宜、体感最强**，但依赖 P1 的归档索引。

## 6. 我需要你拍板的三件事

1. **展开的语义**：就地还原（替换卡片节点）还是追加到尾部？我推荐**就地还原**——因果顺序不变，且「再收起」是同一个原语。代价是从该点起前缀全废（你不在乎）。
2. **询问子 agent 到底给不给读工具**：纯「宿主喂」需要两轮回路；给一支 2 参数 `span_read` 则一轮到位但违背你的洁癖。我推荐**纯喂 + 结构化 need 回路**。
3. **折叠的触发者**：巡航「自己动手折」，还是只「标注 + 建议」，由引擎按票执行？我推荐**后者**——判定与执行分离，才好审计、好回滚、好做 A/B。
