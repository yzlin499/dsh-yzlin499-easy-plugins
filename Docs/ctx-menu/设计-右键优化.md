## 0. 一句话设计

**一个只追加、不破坏任何现有行为的右键动作层**：捕获阶段接管 → 「与外壳条件互补」的门外规则 → 命中锚点 →
用官方 `primitives` 的 `Menu` 渲染在官方 `shell.overlay` 槽里 → 动作表同时供自绘右键与官方菜单插槽两个入口使用。

- **R1（侧栏行）不自绘**：程序化点击官方 ⋯ 按钮，零重绘复用官方菜单。
- **R2/R3（正文文件行）自绘**：官方无插槽，只能 DOM 接管；路径**零解析**（读官方已渲染的隐藏 span）。

## 1. 接管规则（全设计最关键的一条）

### 1.1 为什么必须"互补"而不是"无条件接管"

【权威依据】外壳（Electron 主进程）的菜单只有两个分支会弹（`lib/main.js:11137-11170`，我已逐行复核）：
`isEditable` → 撤销/重做/剪切/复制/粘贴/全选；否则 `selectionText.length > 0` → **只有「复制」**；
两者都不成立 → `items` 为空 → **什么都不弹**。

而**渲染进程 `preventDefault()` 会抑制外壳菜单**（不是叠加）：
Blink 的默认动作门是 `if (!event_->defaultPrevented() && !event_->DefaultHandled() && is_trusted_or_click) { …默认处理器… }`
（Chromium `event_dispatcher.cc:465-469`，【子调研】给出），而"显示菜单"正是默认动作 → 被跳过 →
Electron 的 `context-menu` 不再触发。且**客户端无法补救**：preload 无相关 IPC，主进程菜单不可编程唤起。
Electron 官方文档也确认"默认不弹任何菜单"（[Context Menu](https://www.electronjs.org/docs/latest/tutorial/context-menu)）。

> 诚实标注：我**没能在本环境做 UI 实测**（无法往 Electron 页面注入验证），此条按"Chromium 源码 + 官方文档"取高置信度。
> **但设计不赌它**：下节的门外规则在"会抑制"和"不抑制"两种假设下都安全——因为接管只在
> "外壳本来就不弹"的条件下发生。

### 1.2 门外规则（`gate.js` 的全部职责）

```js
const SKIP = '.xterm, [data-document-preview], [role="menu"]'
const isEditable = (el) => {                       // 对齐外壳 isEditable（保守取并集）
  const e = el.closest('input, textarea, [contenteditable=""], [contenteditable="true"]')
  return e !== null && !e.disabled && !e.readOnly
}

function gate(ev, ctx) {
  if (ev.button !== 2) return null                       // 只处理右键
  if (ev.defaultPrevented) return null                   // ★别人已接管 → 退让（先到先得）
  const t = ev.target instanceof Element ? ev.target : null
  if (t === null || t.closest(SKIP)) return null         // ★别人的地盘（终端/文档预览/已开菜单）
  if (isEditable(t)) return null                         // ★C1：外壳会弹编辑菜单 → 放行
  if (String(window.getSelection()?.toString() ?? '').trim().length > 0) return null  // ★C1：外壳会弹「复制」→ 放行
  const hit = matchAnchor(t)                             // 锚点表（§4）
  if (hit === null) return null                          // 无可追加项 → 连 preventDefault 都不调
  return hit
}
// 调用处：const hit = gate(ev); if (!hit) return; ev.preventDefault(); /* 绝不 stopPropagation */ showMenu(...)
```

要点：
- **不 `stopPropagation()`**：xterm 的右键选词、pdf.js 在 `window` 上的监听都靠冒泡；stop 会连坐。
- **排除区三项**：`.xterm`（终端）、`[data-document-preview]`（文档预览，含 pdf/excel）、`[role="menu"]`（任何已开菜单）。
  Excel/luckysheet 用 React `onContextMenu` 且**不** preventDefault → 我们不接管它会双弹，接管更会双弹，**必须排除**。
- `ev.defaultPrevented` 是唯一的"先到先得"仲裁：同一 capture 目标上按注册顺序跑，**探不到"将要接管"**。

## 2. 渲染层（复用官方组件，不自造 UI）

【子调研 + 我复核】`@deepseek-ai/dsh-client-ui-primitives` 是**平台种子模块**（static seed table 共 9 个：
`react`、`react/jsx-runtime`、`react-dom`、`react-dom/client`、`@deepseek-ai/cordis`、
`@deepseek-ai/dsh-client-store`、`@deepseek-ai/dsh-client-ui-slots`、`@deepseek-ai/dsh-client-ui-primitives`、
`@deepseek-ai/dsh-client-ui-dockkit`）→ **第三方 client 半侧直接 `require` 即可，零声明**。
可复用：`Menu` / `MenuSurface` / `MenuItemButton` / `Tooltip` / `Icon*` / `writeClipboard` / `useDismissOnOutsidePointer` …

**指针定位的官方做法**（`portal:true` + 零尺寸矩形，位置会被夹在视口内 12px 边距）：

```js
h(P.Menu, {
  open: true, portal: true, compact: true,
  anchor: h('span', { style: { display: 'none' } }),
  getAnchorRect: () => ({ left: x, top: y, right: x, bottom: y, width: 0, height: 0 }),
  onClose: close,
  children: rows.map(r => h(P.MenuItemButton, {
    key: r.id, icon: r.icon, danger: r.danger, separatorBefore: r.separator, shortcut: r.shortcut, onSelect: r.run,
  }, r.label)),
})
```
`Menu` 自带外部点击/Escape 关闭与键盘走查，**不要**再自己监听 document 关闭。

**落点 `shell.overlay`**（官方 `layout` 声明的 `list` 槽，`replaceRisk: none`）：
- 容器 `<div data-shell-overlay>`：`z-index:20; pointer-events:none; position:absolute; inset:0`，
  但 **`.overlayLayer > *` 自动 `pointer-events:auto`** → ⚠️ **入口根节点必须按内容收缩，不能 `inset:0`**，否则整个 App 点不动。
- 注册用 `ctx.slots.inject('shell.overlay', () => ctx.slots.register({ name:'shell.overlay', id:'dsh-ctx-menu', order:900 }, () => h(MenuHost,{ctx})))`。

### ⚠️ client 半侧不能有 `src/*.js`（子调研初稿的错误，我已核实纠正）

【实测复核】`dsh-client-modules/lib/client.js`：

- `const CLIENT_CHUNK = /^client\.[A-Za-z0-9][A-Za-z0-9._-]*\.js$/`（**L470**）
- `require.async('./x')`：不以 `./` 开头走 `import(spec)`；以 `./` 开头则 **必须匹配 `CLIENT_CHUNK`**，
  否则抛 `invalid relative chunk request`（**L711**）
- `chunkUrl` 要求包 URL 以 `${row.id}/client.js` 结尾（**L484**）⇒ **分块必须是 `client.js` 的同目录兄弟文件**
- 分块自身要用 `__ModuleLoader__.load({ id, chunk: 'client.<name>.js', factory })` 注册（`chunk` 字段校验见 **L571**）
- 官方先例：`dsh-client-ui-sidebar-terminal/lib/client.js:167` → `require.async("./client.terminal.js")`

⇒ **结论**：plain `require('./src/gate.js')` 会直接抛错；`src/anchors.js` 这类路径**根本加载不到**。
M1 把逻辑**全部内联在 `client.js`**（与仓库现有 5 个插件一致，最省事）；只有确实需要拆时才用
`client.<name>.js` 分块 + `require.async`。

§4 的锚点表因此放在 `anchors.json`（Node 可读），client 半侧内联同一份选择器；
用 `test/` 里的一条**一致性断言**（解析 `client.js` 文本 vs `anchors.json`）防止两边漂移。

## 10. 根因复盘（2026-10-15）：一个 `TypeError` 引发三层故障

**症状**：R1 正常；正文 chip 右键无反应；随后连 Alt+右键诊断面板也不出来了。

**真实根因**（新加的"直接渲染 MenuHost / buildRows"单测一句话打出）：

```
TypeError: t is not a function    at buildRows
```

`readLocale()` 把 `desktop.t` 存成了**字典对象** `DICT[active]`，而 `buildRows` / 菜单按 `t('openFile')` **当函数调用**。
于是**第一次打开菜单就抛异常**，触发这条链：

1. React 渲染崩 → 2. slots 层把该注册**退役**（`reportEntryError(..., { abdicate: true })`，
   `entriesOfSlot` 跳过 `abdicated`，见 `dsh-client-ui-slots/lib/index.js:286,456`）→
   3. overlay 槽里那条注册永久 `active: false`（我从运行时 Inspect 看到过），**菜单从此不再渲染**；同时
4. 因为诊断面板当时也走同一条渲染链路，**它跟着一起失效**——这就是"连诊断都打不开"。

**三条修正**（v0.1.4）：
1. `t` 改成真正的取词函数（`makeTranslator`），并补上 buildRows / MenuHost 的直接渲染单测——这类测试本该一开始就有。
2. **菜单不再占用任何槽**：用平台种子模块 `react-dom/client` 自建 React root 挂到 `document.body`，
   外面套 `MenuBoundary` 错误边界（崩溃会写进 `__DSH_CTX_MENU__.errors` 并显示提示，而不是静默消失）。
3. **诊断面板直挂 DOM**，完全不经过 React / 槽；并新增启动进度标记 `window.__DSH_CTX_MENU__`
   （`phase` 走 `factory → apply-start → gate:ok → … → ready`，任何一步失败写进 `errors`）。
   另外锚点按"同一组件的所有变体"补齐：两类 chip 的差别只是 `fileLink` 类名与 title 是相对还是绝对。

**教训**：
- 官方插槽的注册**会因渲染异常被退役**，这是"静默失效"的温床；凡是**诊断类**功能都不该走渲染链路。
- 纯逻辑单测（gate / 锚点）**发现不了渲染层崩溃**；补上渲染层测试后这个 bug 立刻现形。
- 排查这类"没反应"时，先用运行时 Inspect 看注册的 `active`，再用 `__DSH_CTX_MENU__.state()` 看进度与错误，
  比猜快得多。

## 11. 二级菜单与「是否依赖 dsh-better-sidebar」的决策（2026-10-15）

**需求**：关联应用动辄二三十个（实测 25 个：VS Code、WPS 系列、记事本、7-Zip、百度网盘、Foxmail、
Godot、hl2.exe、MuMu 模拟器…），必须收进二级菜单，并对齐官方文件菜单的分组观感。

**调研到的两个事实**：
1. **官方 `primitives` 的 `Menu` 本来就有二级菜单**，但只在 **`items` 数据接口**上：
   `entry.submenu = [...]` → 渲染为嵌套 `MenuSurface`（`aria-haspopup="menu"`，hover/聚焦/点击展开），
   `onSelect` 对子条目回传**子条目 id**；分隔线是 `{ type:'separator', id }`，分组标签是 `{ type:'label', id, text }`。
   `children`（`MenuItemButton`）这条路径没有 submenu。
2. **`dsh-better-sidebar` 的菜单不可复用**：其 client 半侧只 `exports.apply` / `exports.inject`（L27076-27077），
   唯一公开面是 `ctx.provide("betterSidebar", service)`，而该服务是 tab / viewer / fileIcon 注册表 +
   打开类动作（`openFile` / `openTab` / `activateTab`…），**没有菜单渲染 API**。它自己的右键菜单同样是
   用官方 primitives 的 `Menu`（`items` + `submenu`）搭的。

**决策（含 2026-10-15 当天的修订）**：
- **菜单用官方 primitives 自建**（`items` + `submenu`），不用 `children`；这样观感与官方文件菜单、
  better-sidebar 的菜单天然一致，且不引入跨插件内部依赖。
- ~~能力层面依赖 better-sidebar 的公开服务~~ → **已移除**（用户决定）：它和官方 `sidebarRight.openResource`
  功能重叠（两者都是"在侧边栏打开"，只是渲染容器不同：官方右侧栏 vs better-sidebar 自己的 editor tab），
  只保留官方通道。现在本插件**零第三方依赖**。
- **新增外层「在 <应用> 中打开」行**（用户要求）：**"默认应用"取的是 DSH 自己那个「在应用中打开」控件里
  用户点过的应用，而不是系统关联**。官方实现（`dsh-client-ui-open-in-app/lib/client.js`）：
  - `choice = createSnapshotStore("", { persist: { name: "dsh.open-in-app.choice" } })`（L69）；
  - `currentApp() { const apps = this.apps.getSnapshot().filter(id => APP_LABEL_KEY[id] !== undefined);
    const choice = this.choice.getSnapshot(); return apps.includes(choice) ? choice : apps[0] }`（L79-83）；
  - `choose(appId) { … this.choice.set(appId) }`（L104-106）——用户在下拉里点一次就被记住；
  - `APP_LABEL_KEY` 是它的**固定目录**（`explorer` / `vscode` / `androidstudio` / `rider` / `intellij` …），
    所以那个菜单只有 4 项，和文件关联列表（二三十项）不是同一份数据。

  持久化格式：`@deepseek-ai/dsh-client-store` 的 `attachPersistence` 是"整值 JSON 写 localStorage"
  （`store.js:111-123`），因此键值形如 `"rider"`（带引号），读取要 `JSON.parse`。
  **实测本机 LevelDB**：`_dsh-app://app · dsh.open-in-app.choice = "rider"`，而系统关联是 `.md → VSCode.md`
  —— 两者确实不同，这正是"我改了 Rider 却总显示 VS Code"的根源（改的是 DSH 控件里选的应用，不是系统默认）。

  实现：`preferredAppId()` 读该键 → `pickPreferredApp(apps, choiceId)` 在**本文件自己的关联列表**里匹配
  （id 精确 → `APP_ALIASES` 别名/名字互相包含）→ 用列表条目自己的 id 调 `openWorkspacePath({ path, application })`；
  匹配不到退回系统默认（列表里 `default: true` 的那项），再不行退回 `openWorkspacePath({ path })`（不带 `application`）。
  为什么必须落到列表条目上：只有 Host 认得的 id 才会被 `openWorkspacePath` 接受。
  Alt + 右键的诊断面板新增打印 `open-in-app.choice`，排查这一层时一眼可见。

  **踩坑（v0.1.7 → v0.1.8）**：第一版匹配用"归一化子串包含 + 列表顺序先到先得"，
  结果 `explorer` 命中了排在前面的 **`internet explorer`**（`internetexplorer` 里确实包含 `explorer`），
  菜单显示成「在 Internet Explorer 中打开」。改为**分级匹配**：每级**全表扫完**才进下一级
  （① id 全等 → ② **id 主干**相等（去路径/扩展名：`explorer` ↔ `explorer.exe`）→ ③ 名字全等 →
  ④ 整词命中且**通用词白名单外**，多候选取"多余词最少"者），并加了回归测试：
  IE 排在 explorer.exe 前面必须选 explorer.exe；列表里只有 IE 时必须返回 null（宁可退回系统默认，也不开错应用）。
  教训：**模糊匹配 + 先到先得**对"通用词 id"（explorer / code / studio）就是错配机器，必须靠主干或全等认定。

  **踩坑 2（v0.1.8 → v0.1.10）**：分级匹配上线后仍出现「在 **hl2.exe** 中打开」（用户机器上
  `f:\steamlibrary\…\sdk\hl2.exe`，半条命 SDK 遗留的注册表项，且它没有 `SupportedTypes`，
  被 Windows/枚举器当作"什么都能开"的候选混进了 `.md` 的打开方式列表）。
  根因在**别名分词**：`explorer.exe` 切成 `['explorer','exe']`，`explorer` 被通用词表挡住，
  但 **`exe` 漏网**（长度 3、不在表内），而 `hl2.exe` 的 id/名字切词恰是 `['hl2','exe']` → **`exe` 命中**。
  也就是说：**任何名字里带 `.exe` 的条目都可能被 `explorer` 的别名匹配上**。
  修正：① 别名**先去扩展名再切词**（`aliases.map(idStem).flatMap(tokensOf)`）；
  ② 通用词表补 `exe/com/bat/cmd/lnk/app/dll/run`；③ 整词级要求 needle 长度 ≥ 4。
  用用户真实列表回归：`explorer → null（退回系统默认）`、`rider → JetBrains Rider 2026.2.1`、
  `vscode → Visual Studio Code`。
  教训：**别名表里的任何"碎片词"都会变成判据**；把别名先归一成主干再分词，是这类匹配唯一稳妥的顺序。

  **踩坑 3（v0.1.10 → v0.1.11）**：用户报"鼠标一移过去二级菜单就消失"。
  根因是**我自己引入的**：v0.1.5 为了防"二三十项子菜单溢出屏幕"加了
  `.ctxm-menu [class*="_submenu"]{max-height:62vh;overflow-y:auto}`，
  而官方 CSS 本来就靠 `.submenu::before` 这座 10px 宽的::before 桥跨过 `left: calc(100% + 10px)` 的间隙
  （鼠标走在桥上仍算在父行内 → 不触发父行 `mouseleave` → 子菜单不收）。
  **给子菜单加 `overflow` 会把伸出元素外的那座桥一起裁掉** → 手一进间隙父行就 `mouseleave: setOpenSubmenuId(null)` → 子菜单秒收。
  修正（同时不再依赖 CSS-module 哈希类名，改用 `role` 属性定位）：
  ```css
  .ctxm-menu [role="menu"]{max-height:62vh;overflow-y:auto;left:calc(100% - 2px)}          /* 钳制 + 直接消掉 10px 间隙 */
  .ctxm-menu [role="menuitem"][aria-haspopup="menu"]::after{…left:100%;width:14px}          /* 桥补在未被裁剪的父行上 */
  .ctxm-menu-flip [role="menu"]{left:auto;right:calc(100% - 2px)}                           /* 贴右边缘时向左展开 */
  ```
  翻转判据（JS）：`state.x + 380 > window.innerWidth` → 加 `ctxm-menu-flip`
  （官方对子菜单**没有任何视口钳制**，贴边时它会整条跑到视口外，够不到）。
  教训：**给别人的浮层加 `overflow` 之前，先看它有没有用 `::before` 之类的"扩展命中区"**；
  另外选择器尽量用 `role`/`aria-*`，别绑 CSS-module 的哈希类名。

**踩到的坑（照 better-sidebar 的先例处理）**：官方子菜单表面**没有任何视口钳制**（纯 CSS `left: calc(100% + 10px)`，
无 `max-height`），二三十项会直接溢出屏幕。better-sidebar 为此写了 `menu-flip.ts`（打开自己的子菜单时写 body 属性翻转几何）。
本插件的办法（v0.1.11 修正后）：给自家菜单卡加 `listClassName: 'ctxm-menu'`，用**作用域 CSS**
（选择器全部用 `role`/`aria-*`，不绑 CSS-module 哈希类名）钳制高度、补命中桥、按视口翻转 —— 只影响自己的菜单。

## 12. DSH 0.2.1 契约迁移（2026-10-26，插件 0.2.0）

**症状**：用户升级 DSH 后「右键什么应用都没有了」——菜单还在，但整组桌面动作消失。

**根因（实测，非推断）**：
1. 运行时客户端服务目录只剩 `layout / locale / sessions / slots / theme / timer / uiWorkspace / workspaces`，
   查询 `remote.session` 直接报 `no catalogued Service named "remote.session"`。
   客户端 Builtin 也只剩 `ctx / React / host / styles / console`
   （`cordis_inspect_query` client `Service.listService` / `Builtin.listBuiltins`）。
2. 官方 `open-in-app` 已改为「宿主半侧注册自己的 webServer 路由（`/open-in-app/apps`、`/icon`、`/open`）+ 客户端 fetch」，
   宿主侧用 `@deepseek-ai/dsh-native-command` 与**编译期应用目录**（不再枚举系统关联）。
3. **但能力本身还在宿主侧**：`sessionController` 仍暴露 `workspacePathApplications` / `openWorkspacePath` /
   `canOpenWorkspacePath` / `workspaceDesktop`；`sessions.get` + `workingDirectory.get` 能取会话 cwd。
   只是这条面**不再对动态插件的客户端半侧开放**。
4. `sidebarRight.openResource` 没有客户端服务了（deliverables 里的 `openResource` 是它自己 tab 的 actions）
   → 「在 DSH 中打开」在 0.2.1 无公开入口。

**采用的方案（用户选 A：完整迁移）**：
- **宿主半侧从"空实现"升级为薄代理**（`index.js`）：`inject = ['webServer']`，注册六条同源路由
  `/ctx-menu/{capabilities,apps,cwd,read,open,reveal}`，分别代理 `sessionController.*` / `sessions+workingDirectory` / `node:fs`。
  鉴权与官方一致：`connection.requestRejection(req)`；只接受绝对路径；读文件校验存在/非目录/大小上限（文本 2 MiB、字节 32 MiB）；
  启动与定位一律交给 `sessionController`（它内部还有一次 `verifyDesktopPath`）。
- **客户端新增「平台桥」**：自有路由优先，`fetch` 失败/404 时**回退 0.2.0 的远程服务**，
  因此同一份 client.js 在 0.2.0 与 0.2.1 上都能工作（旧的 `remote.session` / `remote.workspaceFiles` 路径保留为兜底）。
- **能力缺失即隐藏**：「在 DSH 中打开」只在 `sidebarRight.openResource` 存在（0.2.0）时出现。

**顺带修正的哨兵误判**（`check.mjs` / `anchors.json`）：0.2.0 时它断言"primitives 的文件在磁盘上"，
0.2.1 把实现并入 `dsh-web-frontend` 打包产物后一路误报，**却漏掉了真正断掉的服务改名**。现在分两类断言：
`asarExpect`（单文件字面量：锚点、外壳契约、**宿主服务方法名**、`webServer.register` 契约、打包产物里的
`MenuItemButton`/`MenuSurface`/`fileMention`）+ `asarScan`（跨文件出现次数：客户端仍 require 的**种子模块 id**，
它们按运行时 id 提供、不在磁盘上存在）。右键基线新增忽略项：内嵌 DevTools（`dsh-experimental-inspector/lib/devtools/`）
与整站打包产物；`dsh-experimental-session-inspector` 因"只在自身拾取遮罩期间监听 contextmenu、不 preventDefault"记入基线并注明。

**新增测试**：`test/host.test.mjs`（16 项：路由注册、鉴权闸、方法不允许、路径校验、读写上限、错误码）、
`test/bridge.test.mjs`（11 项：路由→远程服务回退、请求形状、URL 编码、字节流）。合计 91 项单测 + 11 项静态断言。
